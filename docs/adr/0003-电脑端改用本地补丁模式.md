# 电脑端改用「本地补丁」模式，放弃与上游逐字节一致

**Status:** accepted（2026-09-21）

电脑端 `Windows\` 一直是上游 `Sui-IB/InternalBeyond` 的**纯拷贝**：67 个文件与上游 `9ef2ed12` 逐字节一致、零本地改动，"同步"就是用新文件覆盖。这个状态有一个好处 —— 跟上游永远不会冲突，因为本地没有任何东西可冲突。

2026-09-21 的跨端功能对照查出一批**手机端已有、电脑端没有**的能力，用户挑了 6 项要补（连接测试、精细文件工具、表情包/颜文字、收藏夹、AI 控制播放器、小助手水水）。**决定：电脑端转入「本地补丁」模式** —— 改动以补丁脚本形式落在 `Windows\_patches\`，按**修订项**粒度切分，每项可独立应用、独立验收、独立摘出；同时保留向上游提 issue / PR 的通道。

关键约束来自上游的处置风格（开发者原话，见 `docs/agents/upstream-issue-loop.md`）：**"IB 的改动是按修订单一处处锚定落进单文件提交更新的"**，所以上游**不合并 PR**，而是"把方法逐条搬进主线"。这条决定了补丁的切分粒度必须是"一个可独立搬走的方法"，而不是"一次做完的一坨" —— 否则将来想给上游某一项时，只能连带着把另外五项一起交出去。

## Considered Options

- **继续纯拷贝，不补任何功能**：被否。用户明确要这 6 项，且其中收藏夹、表情包是手机端天天在用、电脑端缺一块的体验。
- **直接改 `InternalBeyond.html`，不留补丁脚本**：被否。一旦与上游再次对齐（上游发版、或将来某项被采纳），改了什么、改在哪，只能靠逐行 diff 反推。补丁脚本把"改了什么"和"改在哪个锚点"固化成可重复的东西。
- **在 fork 上开分支提 PR**：不作为主形态。上游不合并 PR，这个动作的收益只剩"方法被搬走"，而成本是分支要一直跟着上游对齐。仍保留为可选通道 —— 手上已有实现时按惯例挂一个"参考实现"PR 供对照。
- **补丁粒度按"功能"切（6 个文件）**：选用。与上游的"修订项"粒度对齐，便于逐条搬。
- **补丁粒度按"技术动作"切（锚点、注入点各一个）**：被否。上游搬的是"方法"而不是"补丁块"，按技术动作切会让一个功能散在多个补丁里，反而更难搬。

## Consequences

- **电脑端从此不能再声称与上游逐字节一致**。任何"电脑端是不是干净的"这类核对，判据从"文件全等"变成"逐项比对本地补丁台账"。这一条直接影响既有的同步流程。
- 上游发版后需要**重打锚点**：每个补丁的锚点若被上游改动覆盖，补丁会失效，必须逐个复核（沿用手机端既有的锚点式流水线做法）。
- 需要维护一份**差异台账**：本地补丁 ↔ 上游现状。用途有两个 —— 上游发版时判断哪些补丁要重打，以及上游某天采纳了某项时，**撤掉对应补丁**（否则本地会变成重复实现）。
- 6 项按风险分批落地：先做独立、低风险的三项（连接测试、精细文件工具、表情包），验收通过后再动 Chat 面板与播放器，水水小助手排最后（它的知识源是说明书，而说明书要等电脑端补完才写）。
- 「功能对齐」做完之后，两端的"不齐"从"能力缺失"变成"实现差异" —— 这是预期内的代价，不是失败。
